Deux effets distincts

Allocation seule : conserver le montant actuel, puis le repartir. Recalcul + allocation : reconstruire le serveur, puis le repartir. Une hausse reste possible lorsqu'une ancienne valeur de serveur etait fortement sous-evaluee.

Hypotheses et limites

La part CPU correspond aux ressources reservees, pas au taux de charge. Le scenario par composants alloue le socle/CPU/disques par vCPU, la RAM supplementaire par RAM, et les GPU/VRAM par cartes allouees. Aucun amortissement temporel n'est applique.

La capacite inutilisee n'est pas redistribuee dans le scenario central. Le JSON contient des sensibilites a 75 % / 50 % d'allocation de capacite, sans affirmer que ces taux sont observes. Le maximum de VM par hote peut limiter le remplissage : Azure annonce par exemple seulement 32 D2s_v6 sur 192 vCPU. Une allocation 2/192 ne signifie donc pas que 96 de ces VM sont deployables.

Les scenarios issus de la plus grande taille du catalogue, les hypotheses d'hote deja contestees et les variantes GPU restent experimentaux. Ne pas remplacer automatiquement les valeurs. Les reservations bare metal restent a 100 %.
